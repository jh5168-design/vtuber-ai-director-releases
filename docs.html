VTuber AI Director

A local-first live director and speech-tracked teleprompter for character-driven chatting streams. The core rule is simple: you perform; the AI directs.

Overview

The app listens to the streamer, follows progress through prepared dialogue, classifies unscripted speech, selects valuable audience messages, and keeps a forward-looking script buffer ready. Current spoken text stays locked; new events change only future dialogue.

✦
What this is not

It is not an autonomous avatar, voice clone, or broadcast platform. The streamer remains the performer and decides what is spoken.

Primary capabilities

  • Speech-aware teleprompter with conservative fuzzy progress matching.
  • Character profiles with speaking style, humor, examples, and behavioral boundaries.
  • Strict per-character and per-environment memory namespaces.
  • Live rehearsal with simulated audience activity.
  • Bilibili Open Live integration through the official identity-code flow.
  • Local Whisper or supported browser speech recognition.

Requirements

Desktop installers bundle the interface and backend. Model inference and local speech recognition still have their own requirements.

Quick start

For the guided product flow, use the interactive onboarding page. For source development:

# from the repository root cp .env.example .env make setup # terminal 1 make backend # terminal 2 make frontend

Open http://localhost:5173. The application creates a sample character on first start.

Character Studio

A character defines both generation behavior and data scope. Fill in the identity, background, worldbuilding, personality, speaking tone, typical phrases, forbidden behavior, and example dialogue.

Write examples that can be performed

Short, speakable example lines are more useful than abstract adjectives. Combine them with explicit boundaries: what the character would never claim, reveal, or joke about.

◈
Namespace guarantee

Memories, viewer profiles, callbacks, and sessions are always queried with the selected character ID. Switching characters switches the complete context boundary.

Live Rehearsal

Rehearsal uses the same director pipeline as production without connecting to a real room. Choose audience activity from None, Low, Medium, High, or a custom 5–600 second interval.

What to observe

  • The current sentence highlights and advances only after recognized speech.
  • Partial results are visible but do not become trusted history.
  • Improvisation or a topic change invalidates future generations, not current text.
  • Prepared dialogue remains available while replacement content is generated.

Live Stream

Open Live Stream, select a character, choose speech input, and write session instructions. Instructions may describe format, atmosphere, restrictions, interaction style, and required capabilities in ordinary language.

An optional TXT or Markdown manuscript supplies reference content and a persistent resume position. Use Interpret instructions to review the resulting director policy before starting Full Auto.

Memory Studio

Memory Studio separates live-stream and rehearsal data. Each entry records source type, whether it was actually spoken, importance, confidence, and callback usage.

Rehearsal memories never move into production automatically. A selected rehearsal memory can be transferred only after explicit confirmation; its viewer and session association is cleared during transfer.

Model service

Director generation, instruction interpretation, opening topics, and rehearsal viewers share one OpenAI-compatible client. The default local endpoint is http://localhost:1234/v1.

The client negotiates structured output in this order: JSON Schema, JSON object, then prompt-constrained output. It remembers the compatible mode for each service URL and model.

Settings

  • Service URL: the provider base URL ending in /v1 when required.
  • Model: the exact identifier exposed by the provider.
  • API key: optional for local services; required by most cloud providers.
  • Timeout: increase this for slower local models. A 27B model may need tens of seconds.

Speech recognition

Local Whisper is the default. Browser audio is converted to 16 kHz PCM and sent to the local backend over an authenticated WebSocket. Audio is held in memory and split around natural pauses before transcription.

The first use downloads the selected Whisper model into the app’s local model directory. Use the five-second input test to check capture, input level, backend reception, transcription, and playback.

Bilibili Open Live

The integration uses the official Open Live API and the WebSocket transport returned by /v2/app/start. It does not use cookies, room URLs, or public-room scraping.

The streamer enters an identity code for each room. Developer credentials—App ID, Access Key ID, and Access Key Secret—are configured once in Settings. The backend stores them locally and never returns secret values to the renderer.

Supported events

Danmaku, Super Chat, paid gifts, and guard events feed the existing audience selector. Free-gift bursts, likes, room entries, and live start/end events are not mapped.

Architecture

The Electron shell launches a private FastAPI process on an automatically selected loopback port, waits for an authenticated health check, and serves the production React bundle from that process.

Electron main process └─ private loopback token ├─ React renderer ├─ FastAPI HTTP + WebSocket ├─ SQLite persistence └─ local model / external compatible API

Renderer sandboxing and context isolation are enabled. Node integration, arbitrary navigation, and popups are disabled. Only microphone media requests from the app are allowed, subject to OS permission.

Privacy & data

The backend binds only to 127.0.0.1. Each desktop launch creates a random token held in an HttpOnly, SameSite cookie inside an in-memory Electron session. Every HTTP route and WebSocket connection is authenticated.

The local database lives in the Electron user-data directory. Whisper models are stored in its model cache. Local recognition does not send microphone audio to a browser vendor or public network.

⚠
Current credential limitation

Saved model and Bilibili secrets use the local SQLite settings table. Migration to the operating system credential store is not implemented. Protect the user-data directory and backups.

Troubleshooting

The model connection fails

Confirm the service is running, the base URL is correct, and the configured model name matches the provider. Local services usually do not need an API key. Increase the timeout for slow local inference.

No microphone is available

Allow microphone access in both the operating system and app. Close other software that may hold the device, refresh microphones, and run the input test again.

Local Whisper will not load

Confirm that the machine can reach Hugging Face on first download, or set a mirror through HF_ENDPOINT. A previously downloaded local model directory can also be selected.

Bilibili does not connect

Confirm developer credentials in Settings, then verify the current identity code. Unpublished Open Live projects can connect only to the developer’s own room.

Known limitations

  • Desktop preview builds are unsigned and not notarized.
  • Automatic updates and crash recovery are not implemented.
  • Physical microphone behavior requires acceptance testing on each target machine.
  • Windows runtime behavior must be verified on Windows; a macOS build cannot certify it.
  • Browser speech recognition is not guaranteed inside Electron; use Local Whisper.
  • Real Bilibili room reception requires an approved project and a manual live-room test.
